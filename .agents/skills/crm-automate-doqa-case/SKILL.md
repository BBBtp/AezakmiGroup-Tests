# Автоматизация CRM-кейса

## Сначала установить контракт

1. Прочитать `AGENTS.md`.
2. Прочитать `docs/ARCHITECTURE.md` и `tests/ARCHITECTURE.md` перед изменением границ слоёв.
3. Прочитать `docs/WORKFLOW.md`, если задача связана с DoQA, Allure или публикацией.
4. Проверить `git status --short`; сохранить несвязанные изменения пользователя.
5. Найти существующее покрытие по названию, endpoint, UI-тексту и Allure ID через `rg`.

Не начинать реализацию по одному названию кейса. Получить предусловия, шаги, ожидаемый результат
и точный ID.

## Работать с DoQA безопасно

Если задача включает чтение, изменение статуса или публикацию в DoQA, использовать установленный
`doqa-mcp-workflow` и доступный MCP DoQA. Не обходить доступный MCP прямым HTTP.

Соблюдать цепочку одного кейса:

```text
manual #A -> planned #A -> automated #A
```

- Прочитать кейс и подтвердить совпадение сценария до изменения статуса.
- При нескольких кандидатах остановиться и запросить выбор.
- Выполнять safe normalization сначала в dry-run.
- Сохранять ETag/versionUuid при записи.
- Использовать `A` как единственный `allure.allureId('A')`.
- Не создавать второй кейс ради связи с уже написанным тестом.
- Не публиковать без явного запроса пользователя, завершённого preflight и непустого отчёта.
- Разрешено публиковать failed/broken результаты: они должны быть валидно связаны с кейсами и
  пройти triage после загрузки.
- Не создавать дефект по одному факту падения. Сначала выполнить `doqa_analyze_run_failures`,
  подтвердить классификацию `product`, проверить dry-run и активные дубли.
- Для подтверждённого дефекта вызвать `doqa_create_product_defect` сначала с `apply: false`, затем
  с `apply: true`; проверить DoQA bug ID и ссылку внешнего трекера.
- После публикации проверить test count, progress, run elements, Allure ID и статус кейса.
- Не читать и не выводить `.env`, токены, пароли или storage state.

## Спроектировать сценарий

Прочитать [карту сценариев](references/scenario-patterns.md) и выбрать минимальный набор слоёв.

Соблюдать зависимости:

```text
business test -> fixture/support flow -> @modules/*
@modules/* -> pages -> components -> framework/ui -> locators
support flow -> framework/network|data|lifecycle|playwright
```

- Оставлять в тесте бизнес-шаги и проверки данных.
- Добавлять UI-поведение в page/component и экспортировать только через `@modules/*`.
- Хранить статические и динамические селекторы в `locators/<domain>`.
- Использовать `UiActions` и `UiExpectations`; не вызывать raw locator API из теста.
- Использовать `NetworkController` для navigation, response waits, mocks и request capture.
- Использовать `TestDataFactory` и domain lifecycle для уникальных мутаций.
- Регистрировать компенсацию до создания или изменения данных.
- Использовать `ManagedTestSession`, `AuthSessionLifecycle` и `BrowserDiagnostics` вместо raw
  Page, BrowserContext, storage и browser events.
- Оставлять общий KPI Settings mutation-набор serial.
- Не добавлять retry, sleep, `networkidle`, `force: true` или позиционный locator для маскировки
  нестабильности.

## Реализовать

1. Добавить или расширить locator contract.
2. Реализовать локальное действие в компоненте.
3. Скомпоновать бизнес-поток и наблюдаемые ожидания в page object.
4. Добавить публичный экспорт домена.
5. Добавить fixture или `tests/support/<domain>` только для повторяемого lifecycle/integration flow.
6. Написать тонкий сценарий в `tests/smoke` или `tests/regression`.
7. Добавить ровно один уникальный числовой Allure ID.
8. Обновить архитектурную документацию, если изменились команды или границы.

Не создавать speculative helpers. Сначала найти минимум два реальных потребителя либо оставить
поведение в доменном объекте.

## Проверить

Запустить изменённый сценарий напрямую в правильном project. Затем выполнить проверки из
`AGENTS.md`:

```bash
npm run quality
npm run test:unit
npx playwright test --list
```

Запустить smoke или regression пропорционально риску. Для изменения shared lifecycle, fixtures,
network, authentication или framework выполнить полный соответствующий набор. Не считать тест
зелёным, если он прошёл только после retry.

Перед публикацией сформировать preflight:

- ID и название кейса;
- путь и project автотеста;
- совпадение сценария и Allure ID;
- результат адресного запуска и quality, включая passed/failed/broken/skipped;
- статус кейса `planned`;
- количество результатов в непустом отчёте.

После публикации failed/broken результатов:

1. Прочитать элементы созданного run и выполнить read-only triage.
2. Отделить дефект продукта от ошибки теста и инфраструктуры.
3. Для `product` записать конкретное доказательство наблюдаемого нарушения.
4. Проверить dry-run, отсутствие активного дефекта с маркером `[AUTO][TC-<id>]`.
5. Создать и проверить дефект только после подтверждения классификации.
