# Рабочий процесс автоматизации

## Ежедневный цикл

1. MCP получает из DoQA 5–6 кейсов со статусом автоматизации `planned`.
2. Для каждого кейса выполняется анализ качества и пригодности к автоматизации.
3. Если найдены безопасные проблемы, `doqa_improve_case` нормализует поля и удаляет точные дубли шагов через ETag/versionUuid.
4. Кейс с недостатком бизнес-смысла остаётся на ревью, а не переписывается автоматически.
5. Перед разработкой читаются полные шаги, предусловия и ожидаемый результат.
6. Кейс переводится в работу с optimistic locking через ETag/versionUuid.
4. Создаётся тест в подходящем `smoke` или `regression` файле.
5. Тест запускается адресно. Ошибки исправляются до зелёного результата.
6. Вечером запускается полный regression-набор.
7. `doqa:run` архивирует текущие raw Allure results и загружает их через `/api/autotests/report`.
8. По итогам проверяются статусы кейсов и элементы прогона в DoQA.
9. Утром формируется сводка: passed/failed/broken/skipped, новые ошибки, повторяющиеся ошибки и требуемые баги.

## Команды

```bash
npm run test:types
npx playwright test <file> --project=regression --workers=1
npm run doqa:run -- --project=regression --workers=1
```

Для адресной публикации нескольких тестов:

```bash
npm run doqa:run -- tests/regression/example.regression.spec.ts --project=regression --workers=1
```

## Правила безопасности

- Не выводить токены, пароли и содержимое `.env`.
- Не удалять `[AUTO]` кейсы при очистке дублей.
- Не менять ограничения обычного пользователя без отдельного согласования.
- Пустой DoQA run считать техническим артефактом, а не успешным отчётом.
- После загрузки обязательно проверять `counts.tests` и `progress` через API.

## Критерий готовности кейса

Кейс готов, если:

- есть Allure ID;
- тест стабильно проходит адресный запуск;
- лог объясняет ключевые действия и локаторы;
- отчёт загружен в DoQA;
- в DoQA появился элемент прогона и статус кейса обновился.
