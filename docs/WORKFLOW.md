# Рабочий процесс автоматизации

## Ежедневный цикл

1. MCP получает из DoQA 5–6 кейсов со статусом автоматизации `planned`.
2. Для каждого кейса выполняется анализ качества и пригодности к автоматизации.
3. Если найдены безопасные проблемы, сначала выполняется dry-run `doqa_improve_case`. Только
   после просмотра preview повторный вызов с `apply: true` нормализует поля и удаляет точные
   дубли шагов через ETag/versionUuid.
4. Кейс с недостатком бизнес-смысла остаётся на ревью, а не переписывается автоматически.
5. Перед разработкой читаются полные шаги, предусловия и ожидаемый результат.
6. Кейс переводится в работу с optimistic locking через ETag/versionUuid.
7. Создаётся тест в подходящем `smoke` или `regression` файле. В smoke входят только критические переходы и доступность основных функций.
8. Тест запускается адресно. Ошибки исправляются до зелёного результата.
9. Перед публикацией выполняется `npm run quality`.
10. Вечером запускается полный regression-набор.
11. `doqa:run` исключает setup и результаты без единственного числового `ALLURE_ID`, проверяет
    уникальность ID и загружает архив через `/api/autotests/report`.
12. Команда завершается успешно только после проверки `counts.tests`, `progress`, элементов
    прогона и соответствия Allure ID кейсам DoQA.
13. Утром формируется сводка: passed/failed/broken/skipped, новые ошибки, повторяющиеся ошибки и требуемые баги.

## Команды

```bash
npm run test:types
npm run quality
npx playwright test <file> --project=regression --workers=1
npm run doqa:run -- --project=regression --workers=1
```

Для адресной публикации нескольких тестов:

```bash
npm run doqa:run -- tests/regression/example.regression.spec.ts --project=regression --workers=1
```

## Правила безопасности

- Не выводить токены, пароли и содержимое `.env`.
- Использовать отдельный `DOQA_AUTOTEST_TOKEN`; MCP не принимает секрет в аргументах.
- MCP публикует только файл из `DOQA_REPORT_DIR`, без произвольных путей.
- Не удалять `[AUTO]` кейсы при очистке дублей.
- Не менять ограничения обычного пользователя без отдельного согласования.
- Пустой DoQA run считать техническим артефактом, а не успешным отчётом.
- Не публиковать отчёт после неуспешного локального preflight.
- После загрузки обязательно проверять `counts.tests`, `progress`, элементы и ID через API.

## Критерий готовности кейса

Кейс готов, если:

- есть Allure ID;
- тест стабильно проходит адресный запуск;
- лог объясняет ключевые действия и локаторы;
- отчёт загружен в DoQA;
- в DoQA появился элемент прогона и статус кейса обновился.
